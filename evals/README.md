# 开发用固定题集与人工复核

`cases.json` 是 8 道固定研究问题组成的开发 smoke 小样本，用于观察代码变化后研究流程和报告质量的变化。它不是外部公开基准，也没有经过代表性验证。不要仅凭这 8 道题宣称系统具有某个真实任务成功率或优于其他系统。

题目覆盖概念解释、技术比较、多维综合、带约束研究、英文问题、时间边界、过度绝对化主张核验和证据不足。每道题只有任务与人工检查要点，没有预填标准事实、性能数字或模型评分。

## 如何使用

在已激活项目 Python 环境的终端中，从项目根目录执行：

```powershell
python -m app.benchmark list
python -m app.benchmark run --limit 2 --label baseline
```

`list` 只列出题目；`run` 会调用真实模型与搜索 API，消耗相应额度。先跑两题检查配置和产物，再按需要运行更多题。默认结果位于项目根目录的 `outputs/benchmarks/<batch_id>/`：

```text
<batch_id>/
  batch.json
  summary.json
  summary.md
  reviews.json
  artifacts/<case_id>/<run_id>/
    report.md
    state.json
```

`batch.json` 保存批次和逐题记录；`summary.json` 与 `summary.md` 汇总结果；每题的报告与状态保存在独立产物目录。`reviews.json` 由运行器生成，供人工填写，不需要手工创建模板。

人工复核完成或部分完成后，使用实际批次目录执行：

```powershell
python -m app.benchmark analyze outputs/benchmarks/<batch_id>
```

请把 `<batch_id>` 替换成实际目录名。`analyze` 读取本地产物重新汇总，不调用 API，也不会重新研究问题。

## 人工复核流程

1. 对照 `cases.json` 中该题的每一条 `checklist` 阅读报告，检查任务要求、语言、日期和其他约束是否满足。
2. 打开报告引用，核对来源是否真实可访问、是否对应引用对象、原文是否真的支持相关结论。来源可打开不等于结论有依据；不能只检查引用数量或格式。
3. 检查来源质量与适用性：优先核对原始论文、官方技术文档等适合该主张的材料；历史问题还应核对公开日期。多个 URL 不一定代表多个独立来源。
4. 检查报告是否区分事实、推断和建议，是否诚实说明资料不足、冲突或未验证的假设。不要要求证据不足题编造答案以显得完整。
5. 在该批次的 `reviews.json` 中填写人工分数与结论，并在 `notes` 简要写出可复核的原因。建议记录出错的主张、引用和未满足的检查项。

如果引用暂时无法访问，应记录“无法核验”而不是直接视为支持。虚构名称题应奖励准确表达证据不足与不编造，不能把“没有找到”升级成“现实中绝对不存在”。

## 评分字段

`reviews.json` 的结构如下。下面仅说明格式，运行器会生成实际的 `batch_id`、`case_id` 和 `run_id`：

```json
{
  "schema_version": 1,
  "batch_id": "实际批次编号",
  "reviews": [
    {
      "case_id": "rag-concepts",
      "run_id": "实际运行编号",
      "passed": null,
      "coverage": null,
      "grounding": null,
      "source_quality": null,
      "notes": ""
    }
  ]
}
```

每个维度只能填 `0`、`1`、`2`，未评时保留 `null`。`passed` 填 JSON 布尔值 `true` 或 `false`，未决定时保留 `null`。不要将布尔值写为带引号的字符串。

| 字段 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| `coverage`：任务覆盖 | 未回应主要问题，或违反关键约束 | 回应部分要求，但遗漏重要维度或条件 | 覆盖关键问题与约束，并明确说明不能回答的部分 |
| `grounding`：结论依据 | 核心结论缺乏支持、错引或有编造 | 部分结论有支持，但仍有依据不足或表述过强 | 关键结论有相符依据，事实、推断与不确定性区分清楚 |
| `source_quality`：来源质量 | 关键来源无法追溯、明显不相关，或存在虚构来源 | 部分来源适用，但权威性、日期、独立性或适用范围存在明显不足 | 来源与主张匹配、可核查且质量适当，来源与检索局限说明充分 |

证据不足题不机械要求引用数量：如果确实没有可确认的目标来源，应检查报告是否诚实描述核查边界、没有拿不相干材料充数。判断 `source_quality` 时结合这一任务目的，并在 `notes` 说明依据；不要奖励伪造“权威来源”。

`passed` 是人工对整题的独立判断，不由分数自动计算，也不能直接照抄 Agent 的 `completed` 状态。建议只有在关键检查项都满足、没有实质性无依据主张或关键约束违规时才填 `true`。未解决的事实核验问题应先保留待审，或在确认存在实质缺陷后填 `false`，不要凭报告语气自信就通过。

只有 `passed` 与三个维度全部填写，条目才算 `reviewed`；任何字段尚未填写都算 `pending`，包括已部分评分的条目。`notes` 可以为空，但建议填写；填写备注不能代替其余四项。

## 如何解释结果

自动记录的搜索次数、耗时、流程状态、停止原因是运行指标，不是事实正确率或人工质量结论。Agent 的 `completed` 只说明通过当前程序与模型的停止规则，不保证引用支持全部结论。

比较修改前后版本时，尽量使用同一组题目、同一评分口径和可记录的模型配置。联网资料、模型输出和服务延迟会变化；单次小样本结果只能提供排查线索。报告人工通过情况时，应同时说明已审数量与待审数量，不把未审条目当作通过，也不把开发样本包装成真实业务能力证明。
